Revised architecture: separate conversation and media context

Both audio sources reach Gemini Live, but never as an indistinguishable mixed stream.

Chrome extension capture
User lane

Open microphone

Mono PCM carries the user's questions and interruptions.

Media lane

Captured-tab audio

Separate PCM carries dialogue and other relevant sound from the selected tab.

Shared visual lane

Changed screen frames

Sampled JPEG frames provide visual grounding and timestamps for both conversation and media context.

Live session A — conversation

Inputs

  • User microphone PCM
  • Changed screen frames
  • Explicit narration triggers
  • Media-context tool results

Responsibilities

  • Open-mic VAD and barge-in
  • Answers to the user's voice
  • Native audio responses
  • Meaningful visual narration
Live session B — silent media observer

Inputs

  • Captured-tab PCM
  • Timestamped screen frames

Responsibilities

  • Transcribe and summarize tab speech
  • Track when tab speech is active
  • Produce no user-facing audio
  • Write a bounded, timestamped context buffer
Backend coordination
Context bridge

Media-context tool

Session A can retrieve recent Session B transcript and summary when a user's question depends on what the video said.

Polite narration

Narration gate

Automatic narration is withheld while tab speech is active and resumes only after a quiet hold period. User questions still receive answers.

Retention boundary

Rolling context, not raw-audio storage

Raw tab audio is streamed and discarded. Only a short in-memory transcript/summary window is available to the conversation and event tools.

Why split the sessions

  • Video dialogue cannot masquerade as the user's voice.
  • Gemini still understands audiovisual context.
  • Narration suppression follows real tab speech.

Cost of the split

  • Two Live connections per extension session.
  • Higher token/audio cost.
  • More session lifecycle and reconnection logic.
